## 1. 硬件理解

### 1.1 设备构成

MAKCM 是一个整机，内部有两块 ESP32-S3：

| 板 | 目录 | 框架 | 角色 |
|---|---|---|---|
| 左板 LEFT | `MAKCM_ESP32s3_Device_Mouse_Left_IDF` | ESP-IDF 5.5.5（原生 CMake，非 PlatformIO） | USB Device 侧，对 Windows 做鼠标透传；同时是 OTA 的唯一入口 |
| 右板 RIGHT | `MAKCM_ESP32s3_HID_Mouse_Right` | Arduino / PlatformIO | USB Host 侧，接下游设备 |

两板之间：**UART1，5 Mbps**。左板侧 `rx_pin=1, tx_pin=2`（见 `main/app_main.cpp` 的 `BridgeTransportConfig`）。

### 1.2 三个对外 USB 口

用户能操作的只有 USB 线，**没有跳线、没有可管理的按键以外的硬件**。

| 口 | 连到 | 说明 |
|---|---|---|
| **USB1** | Windows 主机 | 透传口。**非 BOOT 模式下不能当串口读**；用 esptool 直接探测会导致复位。进 BOOT 模式后会枚举成 COM 口用于刷写 |
| **USB2** | Linux 副机 | 板载 CH343，接到**左板的 UART0（GPIO43 TX / GPIO44 RX）**。这是 OTA 和所有诊断的通道 |
| **USB3** | 下游设备 | 右板的 USB Host 口，接手柄/鼠标等 |

### 1.3 关键：下载模式会锁死

esptool 每次刷完都会打印：

```
WARNING: ESP32-S3 (revision v0.2) chip was placed into download mode using GPIO0.
esptool.py can not exit the download mode over USB. To run the app, reset the chip manually.
```

**这不是提示，是硬约束。** 芯片经 GPIO0 进入下载模式后会一直锁在下载模式，直到**真正掉电**或 EN 复位。

> **刷完固件后，必须把 USB1 和 USB2 都拔掉几秒再插回。**
> 只拔 USB1 不够 —— 设备可能仍由 USB2 供电，左板不会断电，会一直停在下载模式：UART0 完全静默，且下载模式下 ROM 输出走 USB 不走 GPIO43，所以在 115200 上也抓不到开机横幅。

这一条在 2026-08-07 这次会话中造成了数小时的误判，务必遵守。

### 1.4 左板没有 console

`sdkconfig.defaults` 里 `CONFIG_ESP_CONSOLE_NONE=y`（理由：UART0 是协议线，console 输出会和 `STICK_*` 回复交错）。

**后果：左板不回话时没有任何信息** —— 没有 bootloader 日志、没有 panic 输出。唯一的崩溃证据是 flash 上的 coredump 分区（`0x3C0000`）和 `LEFT_STATUS` 里的 `esp_reset_reason()`。

### 1.5 左板 UART0 协议

- 开机 **115200**，收到 `kSpeedSwitch` 序列后切到 **4,000,000**
- 文本命令（`LEFT_OTA_DIAG`、`LEFT_PAIR`、`LEFT_STATUS`、`km.*` …）与 MKOT 二进制帧**共存于同一条线**
- MKOT 解码器只在文本帧边界遇到精确 magic `"MKOT"` 时才接管流
- **文本平面故意不被 OTA maintenance 门控**（`components/makcm_core/secondary.cpp:341` 有大段注释说明原因）。所以"板子进了维护模式所以不回文本命令"这个解释是**错的**

### 1.6 信任边界

- Windows 的 USB1 **永远不是 OTA 入口**
- 更新只能从可信的 Linux 副机（192.168.137.2）经 CH343 → 左板 UART0
- 右板只能通过左板的 UART1 中继到达

### 5.3 解析 / 构造 otadata

otadata 有两份拷贝，分别在 `+0x0` 和 `+0x1000`。每条 32 字节：`uint32 ota_seq` + 20 字节 label + `uint32 ota_state` + `uint32 crc`。
**CRC 只覆盖前 4 字节的 `ota_seq`**，算法是 `zlib.crc32(seq_bytes, 0xFFFFFFFF)`（已在硬件上验证过）。

`ota_state`：`0 = VALID`、`1 = UNDEFINED`、`2 = PENDING_VERIFY`、`3 = INVALID`、`4 = ABORTED`、`0xFFFFFFFF = 未写`
选中的槽 = `(ota_seq - 1) % 2`

```python
# 解析
import struct
d = open("otadata.bin", "rb").read()
for i, off in enumerate((0, 0x1000)):
    e = d[off:off+32]
    seq, = struct.unpack("<I", e[0:4])
    st,  = struct.unpack("<I", e[24:28])
    crc, = struct.unpack("<I", e[28:32])
    print("copy%d seq=0x%08x state=0x%08x crc=0x%08x" % (i, seq, st, crc))
```

```python
# 构造一份 "ota_0 = VALID"
import zlib, struct
def entry(seq, state):
    b = struct.pack("<I", seq) + b"\xff"*20 + struct.pack("<I", state)
    return b + struct.pack("<I", zlib.crc32(b[:4], 0xFFFFFFFF) & 0xFFFFFFFF)
open("otadata_valid_ota0.bin", "wb").write(
    entry(1, 0) + b"\xff"*(0x1000-32) + b"\xff"*0x1000)
```

## 7. 已解决：左板 UART0 静默

结论（双 USB 断电重插后逐一验证）：**板子从来没坏，是探针错了**，两个独立原因叠加：

1. **`raw_probe.py` 发的是死命令。** 它发 `LEFT_OTA_DIAG\n`，但当前固件里 `LEFT_OTA_DIAG` 只是 `LEFT_STATUS` 输出中的一行，不再是可独立执行的命令。正确探针命令是 `LEFT_STATUS\n`。
2. **UART0 波特率会锁存到 4,000,000。** 左板启动时 115200，收到 kSpeedSwitch 后切 4M 且不回落。任何探针必须两种波特率都试（先 115200 后 4000000），只试 115200 会得到"静默"假象。

原§7 的排除表全部成立（镜像、分区表、otadata、NVS、bootloader、DTR/RTS 均已用证据排除），"锁在下载模式"假设在双 USB 断电重插后被否定——板子一直在跑 app。

教训已并入 §9：**先证明探针本身有效（用已知活命令 + 全部候选波特率），再下"板子静默"的结论。**

### 一个顺带发现的真实缺陷

擦除 otadata 后，板子自己启动并把 otadata 写成了 `seq=1 / state=PENDING_VERIFY`。也就是说**一块直接 BOOT 刷写的左板，会以"待确认镜像"的身份启动**，`ota_update_manager.cpp:188-207` 在没有配套 NVS 记录时把它判为 `Fault`（"An untraceable pending image must never mark itself valid"），于是整机 `ota_quiesced` 进入 fail-closed。

对要发给用户的固件来说，这意味着**一次恢复性刷写会产生一台看起来像变砖的设备**。这和已知的 #12 / #17 是同一类缺陷（终态无出口），应当归入待修列表。

## 8. 待办（已与用户确认过的优先级）

### 8.1 先修可观测性（本次会话得出的新结论，最高优先级）

根因不是任何单个 bug，而是**左板没有 console**（§1.4）。板子一旦不回话就是黑箱，只能靠"刷进去再猜"做二分查找，而每一轮都要用户插拔一次线。本次会话大部分时间消耗在这上面。

按用户的工程原则（3：先跑通最小端到端；7：架构决策往长了做），应做成永久设计而非临时诊断构建：

- **启动期**：打开 `CONFIG_ESP_CONSOLE_UART_DEFAULT`（UART0 115200）。`sdkconfig.defaults` 里关掉它的理由是"console 输出会和 `STICK_*` 回复交错"—— 那是**运行期**问题；bootloader 和 `app_main` 早期 app 还没接管 UART，不存在交错。

### 8.3 架构结论（已与用户达成一致）

- 这套 OTA **确实过度设计**：约 9,600 行，缺陷 #12–#20 **全部**在协调/持久化层，传输/烧写路径一个都没有
